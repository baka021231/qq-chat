# 经验与复盘

这里记录做错过的事、踩过的坑，以及从中定下的规矩。和 CHANGELOG 的分工是：CHANGELOG 记“改了什么”，本文记“为什么当初想错了，以后怎么做”。

什么时候加一条：设计上的假设被证明是错的；验收或使用中冒出了设计没想到的问题；流程让人特别累或者出了岔子。每条写几行就够，写清楚“发生了什么、为什么、以后怎么做”。

仓库是公开的：不写 QQ 号、token、OWNER.md 的内容和真实聊天原文，案例用概括的说法。

---

## 2026-10-27 前后台分离

### 前台只会聊天，用起来反而别扭

- **发生了什么**：为了安全，前台被设计成只能聊天和派任务。用起来发现很多小事也得派给后台：带人设语气写日记、看一眼 README 第一段，都要等一两分钟。写日记更麻烦，后台没有人设，写不出她自己的口吻。
- **为什么**：只盯着“前台手上没东西就不会出事”，没考虑使用起来舒不舒服。
- **以后怎么做**：按事情本身分工。几秒能做完、只读或只往后追加、出错影响小的，交给前台；要改文件、跑命令、耗时长的，交给后台。前台的工具按风险分档，并按场景（群友、主人在群里、主人私聊、任务回报）分别给。具体分档见 `docs/FRONT-BACK.md`，待定。

### 拆分时漏掉了“没写在设计里的职责”

- **发生了什么**：拆成前后台后，OWNER.md 里约定的记忆（OUR_STORY、每日日志）没人负责了：前台不能写文件，后台不知道这些约定。开发日志靠后台顺手记着，但只发生在聊天里的事（讨论、部署结果）没人记。
- **为什么**：这些约定写在本地私有文件里，设计和评审时谁都没看到。
- **以后怎么做**：拆分或重构之前，先列一张“现在谁在做哪些事”的清单，本地文件里约定的也要算进去，逐项确认拆完以后归谁。

### AI 会说自己做了其实没做的事

- **发生了什么**：测试时，前台手上没有派任务的工具，提示词里却提到了这个工具。它就在回复里写了一段假装调用的文字，编了个任务编号，说“已经交给后台了”。
- **为什么**：模型会写出“看起来该这么回”的话，而不是去核对自己真的做了什么。这不是故意的，所以靠提醒管不住。
- **以后怎么做**：凡是“做没做”的事实，只认系统记录。派单回执由桥接直接发，不经过模型。提示词里不提模型手上没有的工具。前台回复里出现假调用的痕迹，就整段不发。

### 安全假设必须实测，不能想当然

- **发生了什么**：以为“工具列表为空”就什么都读不到，实测发现用户级 CLAUDE.md 照样会被读进去。以为 `--strict-mcp-config` 能拦住所有外部工具，结果 Chrome 集成照样加载。以为 `--safe-mode` 能放心用，结果它把前台需要的派单工具也关掉了。
- **以后怎么做**：每条安全假设都做正反对照实测：先证明不加防护时问题确实存在，再证明加了防护以后没了。Claude Code 会自动升级，升级后要重跑验证。

### “喊过停”不等于“已经停了”

- **发生了什么**：设计重启善后时，最初写的是“发过中断就算停了”，还打算靠进程号去找旧进程。评审指出：执行端可能还在跑，进程号也可能已经被别的进程用了。
- **以后怎么做**：确认不了的事就按最坏情况处理，不放行。确认不了任务停没停，就继续占着写锁，交给人工确认。个人项目优先选简单、保守的做法。

### 设计评审要有停止条件

- **发生了什么**：设计文档被审了三轮，每轮都挑出了真问题，也每轮都让范围变大，评审本身停不下来。
- **以后怎么做**：评审限定轮数。审阅方要分清“必须先定”和“可以直接补”；小问题由执行方按文档原则自己定，写进修订记录后直接开工。

### 工作量别用模糊的词

- **发生了什么**：最初说前后台分离是“中等工作量”，实际上相当于一个人两到四周。评审中不断补漏洞，又让范围涨了三四成。
- **以后怎么做**：估计工作量直接给时间，并说明按什么标准估的。范围变大时，及时考虑哪些可以砍掉或简化。

### 规矩只写在聊天里会丢

- **发生了什么**：“一次只做一个 PR、做完先别重启、等主人确认”这些规矩，起初只在聊天消息里。新开会话后，AI 就不记得了。
- **以后怎么做**：流程规则写进仓库文档（`docs/FRONT-BACK.md` 第 11 节“执行规则”），新会话也读得到。

### 推送是撤回不了的

- **发生了什么**：准备推送一个只改了文档的分支时，才发现 GitHub 上的 main 一整天没推。分支会带着全部历史一起上传，一推就会把当天所有没检查过的提交公开。同时，一整天的成果也只存在一台电脑上。
- **以后怎么做**：每次合并后，先做隐私检查再推送，顺便备份。推到公开仓库撤回不了，必须先查后推。

### 主人累，是因为身兼三职

- **发生了什么**：一天下来，主人同时在当老板（拍板）、传话员（在两个 AI 之间复制粘贴）和学生（学一堆新概念）。
- **以后怎么做**：汇报按“可以直接拍板”的格式写：一句话结论、要主人定的事、选项和建议、选错了能不能撤回。能撤回的决定直接按建议走，只在撤回不了的事上花精力。尽量让 AI 直接读仓库，减少人工传话。
