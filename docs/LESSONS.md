# 经验与复盘

这里记录做错过的事、踩过的坑，以及从中定下的规矩。和 CHANGELOG 的分工是：CHANGELOG 记“改了什么”，本文记“为什么当初想错了，以后怎么做”。

什么时候加一条：设计上的假设被证明是错的；验收或使用中冒出了设计没想到的问题；流程让人特别累或者出了岔子。每条写几行就够，写清楚“发生了什么、为什么、以后怎么做”。

仓库是公开的：不写 QQ 号、token、OWNER.md 的内容和真实聊天原文，案例用概括的说法。

---

## 2026-10-27 前后台分离

### 前台只会聊天，用起来反而别扭

- **发生了什么**：为了安全，前台被设计成只能聊天和派任务。用起来发现很多小事也得派给后台：带人设语气写日记、看一眼 README 第一段，都要等一两分钟。写日记更麻烦，后台没有人设，写不出她自己的口吻。
- **为什么**：只盯着“前台手上没东西就不会出事”，没考虑使用起来舒不舒服。
- **以后怎么做**：按事情本身分工。几秒能做完、只读或只往后追加、出错影响小的，交给前台；要改文件、跑命令、耗时长的，交给后台。前台的工具按风险分档，并按场景（群友、主人在群里、主人私聊、任务回报）分别给。具体分档见 `docs/FRONT-BACK.md`，待定。

### 拆分时漏掉了“没写在设计里的职责”

- **发生了什么**：拆成前后台后，OWNER.md 里约定的记忆（OUR_STORY、每日日志）没人负责了：前台不能写文件，后台不知道这些约定。开发日志靠后台顺手记着，但只发生在聊天里的事（讨论、部署结果）没人记。
- **为什么**：这些约定写在本地私有文件里，设计和评审时谁都没看到。
- **以后怎么做**：拆分或重构之前，先列一张“现在谁在做哪些事”的清单，本地文件里约定的也要算进去，逐项确认拆完以后归谁。

### AI 会说自己做了其实没做的事

- **发生了什么**：测试时，前台手上没有派任务的工具，提示词里却提到了这个工具。它就在回复里写了一段假装调用的文字，编了个任务编号，说“已经交给后台了”。
- **为什么**：模型会写出“看起来该这么回”的话，而不是去核对自己真的做了什么。这不是故意的，所以靠提醒管不住。
- **以后怎么做**：凡是“做没做”的事实，只认系统记录。派单回执由桥接直接发，不经过模型。提示词里不提模型手上没有的工具。前台回复里出现假调用的痕迹，就整段不发。

### 安全假设必须实测，不能想当然

- **发生了什么**：以为“工具列表为空”就什么都读不到，实测发现用户级 CLAUDE.md 照样会被读进去。以为 `--strict-mcp-config` 能拦住所有外部工具，结果 Chrome 集成照样加载。以为 `--safe-mode` 能放心用，结果它把前台需要的派单工具也关掉了。
- **以后怎么做**：每条安全假设都做正反对照实测：先证明不加防护时问题确实存在，再证明加了防护以后没了。Claude Code 会自动升级，升级后要重跑验证。

### “喊过停”不等于“已经停了”

- **发生了什么**：设计重启善后时，最初写的是“发过中断就算停了”，还打算靠进程号去找旧进程。评审指出：执行端可能还在跑，进程号也可能已经被别的进程用了。
- **以后怎么做**：确认不了的事就按最坏情况处理，不放行。确认不了任务停没停，就继续占着写锁，交给人工确认。个人项目优先选简单、保守的做法。

### 设计评审要有停止条件

- **发生了什么**：设计文档被审了三轮，每轮都挑出了真问题，也每轮都让范围变大，评审本身停不下来。
- **以后怎么做**：评审限定轮数。审阅方要分清“必须先定”和“可以直接补”；小问题由执行方按文档原则自己定，写进修订记录后直接开工。

### 工作量别用模糊的词

- **发生了什么**：最初说前后台分离是“中等工作量”，实际上相当于一个人两到四周。评审中不断补漏洞，又让范围涨了三四成。
- **以后怎么做**：估计工作量直接给时间，并说明按什么标准估的。范围变大时，及时考虑哪些可以砍掉或简化。

### 规矩只写在聊天里会丢

- **发生了什么**：“一次只做一个 PR、做完先别重启、等主人确认”这些规矩，起初只在聊天消息里。新开会话后，AI 就不记得了。
- **以后怎么做**：流程规则写进仓库文档（`docs/FRONT-BACK.md` 第 11 节“执行规则”），新会话也读得到。

### 推送是撤回不了的

- **发生了什么**：准备推送一个只改了文档的分支时，才发现 GitHub 上的 main 一整天没推。分支会带着全部历史一起上传，一推就会把当天所有没检查过的提交公开。同时，一整天的成果也只存在一台电脑上。
- **以后怎么做**：每次合并后，先做隐私检查再推送，顺便备份。推到公开仓库撤回不了，必须先查后推。

### 主人累，是因为身兼三职

- **发生了什么**：一天下来，主人同时在当老板（拍板）、传话员（在两个 AI 之间复制粘贴）和学生（学一堆新概念）。
- **以后怎么做**：汇报按“可以直接拍板”的格式写：一句话结论、要主人定的事、选项和建议、选错了能不能撤回。能撤回的决定直接按建议走，只在撤回不了的事上花精力。尽量让 AI 直接读仓库，减少人工传话。

## 2026-11-02～11-03 语音原声库与连贯性

### 声纹分不清她和别的角色

- **发生了什么**：给原声库标说话人时，起初只看声纹：和她的平均声纹相似度过 0.7 就算她。这个阈值是在远航星上定的，那一章没有林奈。到了拉海洛的任务，林奈的自我介绍能到 0.64–0.71（她自己的台词是 0.69–0.90），混进了候选；改用本章的平均声纹重新打分，错得更多。昨夜群星里只靠声纹认出的 33 句“爱弥斯”，其实是别的角色。上线前查了出来，主人随后提供了剧情页面。
- **为什么**：声纹只量音色，同一个游戏里音色相近的女性角色分不开；在一章上调好的阈值，换一章就不成立。
- **以后怎么做**：说话人以剧情文本为准，台词和剧情对齐后按剧情里的名字标，声纹只用来复核。只有声纹、没有剧情佐证的，单独放一处（`wav-unsure/`），不删，也不混进库。

### 清理时删掉了她自己的原声

- **发生了什么**：主人让清理用不到的文件，助手把库里没进索引的 wav 当成“建库中间产物”全删了。主人拦下来时才发现，其中很多是她本人的台词（太短、太长或还没切分的独白），后来从游戏解包里重新解码恢复。
- **为什么**：按“有没有被用到”判断能不能删，而不是按“这是什么”。对主人来说，她的每一段原声都是素材，不是中间产物。
- **以后怎么做**：她本人的录音一律保留，不管进没进索引；能删的只有合成出来的测试音频和别的角色的台词，记录文件（json、txt）也留着。游戏解包、Whisper 缓存这类以后加章节还要用的，删之前先问。

### 没弄懂问题就动手

- **发生了什么**：主人说连发的三条语音“前后文不太连贯”。助手理解成音高跳变，一口气写了“按音高挑相近原声”的规则并合并进 main。主人说助手没懂，要求先撤回、先分析，再重新梳理原始问题。主人真正的意思是：三条听起来不像同一个人在短时间里连着说。那条音高规则本身也是错的（见下一条）。
- **为什么**：“不连贯”“没那种感觉”是听感，可以有好几种理解；助手挑了最容易量的一种就开始改。
- **以后怎么做**：听感类的反馈，先复述问题、列出几种可能的理解请主人选，再拿证据分析，再提方案。主人同意才写代码，主人试听确认之前不合并。实验放在本地 `workspace/voice-tests/`，不碰线上。

### 好量的指标不一定是对的指标

- **发生了什么**：两次拿指标代替了耳朵。一次是以为合成的音高会跟着原声走，就按音高挑原声；实测 277 Hz 的原声合成出来是 341 Hz，规则作废。另一次是比较连贯方案，CAM++ 声纹相似度给“音色锚定”打的分比“声纹决胜”高，主人听下来却觉得后者更连贯：声纹只量音色，量不到语速、劲儿和说话时的状态。
- **以后怎么做**：要拿一个指标来定规则，先验证它和听感对得上（例如原声之间的声纹相似度确实能预测合成后像不像，音高不能）。指标只用来筛掉明显不行的，最后由主人盲听定。

### 实验要走线上同一条路

- **发生了什么**：第一次“按原声节奏改写”的实验直接调了合成，绕过了线上的文字清洗；改写里的“……”在线上其实会变成逗号，结论要打折扣。自动生成的节奏骨架也漏掉了开头的笑声，还把“送你！”听成了“Sony”，要人工改。
- **以后怎么做**：模拟线上效果的实验从线上的入口（`speak_text`）走，清洗和长度限制都一样；自动工具的输出先抽查再用。

### 每条各自最优，合起来不像一个人

- **发生了什么**：检索按单次 speak 设计：每条语音各挑最贴的原声；为了不总用同一段，还加了“最近用过的让位”。结果同一段对话里的几条各用各的原声，而原声会把各自的整个录音状态带进来；“让位”规则还会把刚用过的那段主动推开，正好和连贯冲突。当天 84 次真实调用里有 56 次是同一对话 10 分钟内的接续语音，不是边角情况。
- **为什么**：设计时只想了“一句话该用什么声音”，没想“几句连着说是什么效果”。链路里根本没有“一段对话”这个单位。
- **以后怎么做**：设计按次调用的功能时，同时想连续几次叠在一起的效果，并用真实记录回放验证。

### 模型有的能力，文档没写我们没用

- **发生了什么**：讨论连贯性时，主人才发现一直以来音色参考和情绪参考是同一段原声。IndexTTS2 支持把两者分开（单独的情绪参考音频、8 维情绪向量），这条路从没试过。
- **为什么**：文档写了“挑哪段原声”，没写这段原声实际以什么参数交给模型、模型还有哪些开关没用。
- **以后怎么做**：接入一个模型时，在文档里列出它的主要开关，写明哪些用了、怎么用，哪些没用、为什么。

### 能让她明确决定的，不靠调分数

- **发生了什么**：“声纹决胜”（给和上一条声纹像的原声加一点分）回放下来有效，但改选的 12 条里有 5 条伤了语气；主人听样本觉得效果不错，但判断实际使用时会很随机。最后定下的是：每条语音由她判断“接着说”还是“换语气”，接着说就整段沿用上一条的原声。
- **以后怎么做**：一个行为能让她明确表态的，就让她表态、后端照办；不靠微调打分间接影响，那样结果说不清，也保证不了。

### 技术上限背后是人设选择

- **发生了什么**：被逗得羞恼、慌张的原声，库里基本没有，挑选和改写都造不出来。一个替代办法是把反应改成库里有的情绪（反将一军、笑着数落），声音是贴了，但主人指出语音和文字的人设就分开了。再往下，是“想要什么样的爱弥斯”，这是主人的决定。
- **以后怎么做**：先查清上限在哪：缺素材时，挑选、改写这类工程优化做不出来，要早说。会改变她性格的方案，助手不替主人选，列出选项交给主人。

### 一次讲太多

- **发生了什么**：排查中途，助手一次给出好几种方案和一大串数据，主人说太多了、要简单点。连续几个小时的排查、结果又不确定，也很耗人。
- **以后怎么做**：一次只讲一个结论和一件要定的事，数据放进文档。大问题拆成很快能听到结果的小实验；先确认现状哪些已经够好（主人觉得现在的语音体验已经不错），再决定还要不要往下挖。
